# ShopAI — архитектура MVP

## 1. Схема

```text
Браузер
  ├── кабинет владельца (React + TypeScript)
  └── публичная витрина /shop/:slug
          |
          v
  Vite proxy (development) / Express static (production)
          |
          v
       Express API
  ├── Auth и HttpOnly session cookie
  ├── Store API
  ├── Product API и загрузка изображений
  ├── AI adapter (Cloudflare Workers AI)
  ├── Public storefront API
  └── Order API
          |
          ├── JSON storage (локальное MVP-хранилище)
          └── uploads/ (изображения)
```

## 2. Frontend

- React 19, TypeScript и Vite.
- Кабинет владельца: обзор, AI-конструктор сайта, каталог, заказы и настройки.
- Форма товара объединяет редактирование и AI-подготовку описания.
- AI-конструктор: бриф, генерация, live-предпросмотр, ручное редактирование, сохранение и публикация.
- Публичная витрина открывается по адресу `/shop/:slug` и отображает сохранённый `siteConfig`.
- Корзина работает в браузере; итоговая сумма и наличие повторно проверяются backend.
- В dev Vite проксирует `/api` и `/uploads` на Express `localhost:3001`.

## 3. Backend

- Node.js 22+ и Express.
- Пароль хешируется через scrypt; исходный пароль не сохраняется.
- Сессионный токен генерируется криптографически случайно; в хранилище сохраняется SHA-256 хеш; браузер получает HttpOnly, SameSite=Lax cookie.
- Приватные маршруты требуют действующую сессию.
- Доступ к товарам и заказам ограничивается магазином текущего владельца.
- Цены и наличие для заказа проверяются на сервере.
- Фотографии проверяются по MIME и размеру; файлы получают случайные имена.

## 4. Основные маршруты

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/auth/register | Создать аккаунт и магазин |
| POST | /api/auth/login | Войти |
| POST | /api/auth/logout | Выйти |
| GET | /api/me | Текущий пользователь и магазин |
| GET/PATCH | /api/store | Получить/обновить магазин и siteConfig |
| GET/POST | /api/products | Список/создание товара |
| PATCH/DELETE | /api/products/:id | Изменить/удалить свой товар |
| POST | /api/uploads | Загрузить изображение |
| POST | /api/ai/product-copy | Подготовить описание и SEO |
| POST | /api/ai/storefront | Сгенерировать контент и конфигурацию витрины |
| GET | /api/orders | Заказы текущего магазина |
| PATCH | /api/orders/:id | Изменить статус заказа |
| GET | /api/dashboard | Фактические показатели магазина |
| GET | /api/public/:slug | Публичные данные магазина |
| POST | /api/public/:slug/orders | Создать заявку на заказ |

## 5. Логические сущности данных

Данные хранятся в JSON-файле `data/shopai.json`. Основные коллекции: users, sessions, stores, products, orders.

- User — владелец аккаунта.
- Session — сессия входа, связанная с пользователем.
- Store — магазин, связанный с владельцем.
- Product — товар магазина.
- Order — заявка на заказ магазина; состав и снимки цены товаров хранятся во вложенном массиве items.

Это логические сущности JSON-хранилища, а не Django ORM-модели и не отдельные реляционные таблицы.

## 6. Хранение

Данные — `data/shopai.json`, атомарная запись через временный файл и rename. Фотографии — `uploads/`. Оба каталога исключены из Git.

JSON-хранилище не рассчитано на несколько экземпляров приложения и интенсивную конкурентную запись. Перед production необходимы PostgreSQL, миграции, транзакции, резервное копирование и объектное хранилище файлов.

## 7. AI-адаптер

- Вызовы выполняются только на backend.
- Настройки: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_AI_MODEL`.
- Используется OpenAI-совместимый endpoint Cloudflare Workers AI: `/accounts/{account_id}/ai/v1/chat/completions`.
- Модель по умолчанию: `@cf/google/gemma-4-26b-a4b-it`.
- Для карточки товара модель возвращает `description` и `seoTitle`.
- Для конструктора сайта модель возвращает поля `siteConfig`.
- Backend проверяет структуру и отклоняет пустой или шаблонный ответ.
- AI-текст — черновик. Пользователь проверяет и редактирует его перед сохранением.
- Если настройки отсутствуют, карточка товара получает явно обозначенный demo-черновик; генератор сайта сообщает, что реальный провайдер не подключён.
- При ошибке настроенного провайдера приложение показывает ошибку, а не подменяет ответ.

## 8. Ограничения и следующие архитектурные шаги

Сейчас один магазин на аккаунт; нет командных ролей. Нет онлайн-оплаты, доставки, налогов и расчёта доставки. Сессии хранятся в JSON-файле; нет CSRF-токена, rate limiting и восстановления пароля. Для production нужна отдельная проверка безопасности.

Следующие шаги: PostgreSQL и миграции, RBAC, object storage, мониторинг/логирование, интеграции платежей/доставки, нагрузочные и security-тесты.


## 9. Развёртывание в Cloudflare Workers

- Frontend: Vite build в `dist/`, раздача через Workers Static Assets с SPA fallback.
- API: Express на Cloudflare Workers через `cloudflare:node` и флаг `nodejs_compat`.
- D1 binding `DB`: версионируемая JSON-запись приложения для MVP; optimistic revision update предотвращает silent overwrite при конкурентной записи.
- D1 table `uploads`: бинарные фотографии товаров и Content-Type; лимит 1,7 МБ на изображение из-за максимального размера BLOB в 2 МБ.
- Secrets: `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN`; модель задана как Worker variable.
- Публичный маршрут `/shop/:slug` отдаётся SPA, API и изображения направляются в Worker.
- Для production-масштабирования JSON snapshot следует заменить на нормализованные D1-таблицы и транзакции.
